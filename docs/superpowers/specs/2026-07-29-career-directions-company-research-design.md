# 动态岗位方向与企业研究链路升级设计

日期：2026-07-29

## 目标

本次升级同时解决：

1. 岗位方向被四个静态分类限制、证据匹配过窄的问题。
2. 企业研究虽然收到企业名称与官网，但未读取来源网页正文，导致研究经常为空的问题。

实现必须保持本地优先、旧数据兼容、千问 Key 不离开当前浏览器同源请求、无需新增第三方搜索 Key。

## 已确认决策

- 旧四个岗位方向迁移为可删除、可调整状态的初始方向。
- 后续岗位方向不再由代码固定，数量不设上限。
- 企业研究采用“千问联网搜索发现 URL + 后端网页正文抓取清洗 + 千问结构化归纳”。
- 不依赖仅由特定模型支持的 `agent_max` 网页抓取。
- 用户提供的企业名称、官网和岗位名称始终优先于模型推断。

## 根因

### 岗位方向

`src/domain/scoring.ts` 中的 `ROLE_TAXONOMY` 固定四个方向，`buildRoleDirectionScores` 仅扫描已确认 claim 的标题和说明是否包含静态关键词。它没有联合使用：

- EvidenceSpan 原始引用；
- 经历组织、角色与项目背景；
- 同一经历中的责任、行动和结果组合；
- 独立的证书、语言和 AI 应用资料；
- 同一证据在不同岗位下的迁移角度。

因此，大量有价值但没有命中精确词面的证据得到 0%。

### 企业研究

企业名称和官网已经写入 JD 记录并进入研究请求。千问原生联网参数也已开启，但当前搜索 Provider 和生产 Worker 将搜索生成的摘要重复保存为每个来源的 `content`，没有读取 URL 网页正文。

当千问搜索未返回 `search_info.search_results` 时，系统得到空来源，随后按照“不编造企业事实”的规则返回无可靠信息。搜索失败、网页读取失败和真正无结果的状态也没有完整分离。

## 架构

### 一、职业方向领域层

新增以下可持久化实体：

- `CareerDirection`：方向名称、来源、状态、匹配度、证据、缺口、岗位名称、关键词与建议。
- `CareerEvidence`：证据来源、原文、匹配角度、直接/迁移/潜力类型、强度和表达建议。
- `CareerDirectionFeedback`：感兴趣、排除、已了解、成本过高和查看更多类似方向。
- `CareerInspirationBatch`：一次千问推荐批次、阶段状态和部分成功结果。

IndexedDB 升级时，若还没有职业方向，则写入原四个方向作为 `default` 初始记录。迁移只运行一次；之后用户可以删除或改变状态。

### 二、完整档案证据层

建立独立的 `careerEvidenceService`，联合读取：

- Experience；
- confirmed Claim；
- Claim 对应的 EvidenceSpan 原始引用；
- 经历的组织、角色、项目和时间；
- ProfileMaterial 中的证书、AI 应用和语言能力。

服务把同一经历拆成责任、行动、结果、能力、工具、AI、证书等证据单元。证据保留原始 ID 与引用，不在本地规则中创造新事实。

方向分析按单个方向重新组织证据：

- 直接相关：职责或结果直接对应岗位任务。
- 能力迁移：事实存在，但目标岗位职能不同。
- 兴趣或潜力：只有研究、学习或弱信号。
- 证据不足：岗位需要但档案无可核验证据。

### 三、岗位灵感服务

新增独立 `/api/career-inspiration` 接口。

输入包含完整档案证据、已保存方向、已排除方向和历史反馈。千问输出 5–8 个方向，区分直接延伸、相邻迁移、复合和探索方向，并必须引用证据 ID。

服务执行：

1. 输入裁剪与隐私边界检查；
2. 千问结构化生成；
3. Schema 校验；
4. 格式异常时自动重试一次；
5. 单卡校验和标准化去重；
6. 保存部分成功结果。

用户可保存、排除、换一批、查看更多类似方向。被排除方向不会在下一批重复；保存方向不会被新批次覆盖。

### 四、企业研究服务

保留现有千问联网搜索作为 URL 发现层，并增加：

- `companyIdentityService`：企业名称标准化、官网校验和同名状态。
- `companySearchService`：按官网、文化、人才、岗位、业务五类构造搜索。
- `webContentService`：安全获取公网 HTTP(S) 页面，阻止本地/内网地址，限制响应大小和时间，清洗 HTML、菜单、页脚、脚本、重复段落。
- `companyResearchService`：保存来源正文与抓取状态，再调用千问生成企业画像。
- `interviewResearchService`：使用企业画像、JD 和简历证据生成能力矩阵、面试重点与问题。

用户提供官网时，官方类搜索优先限定该域名。单页抓取失败只标记该来源，不中止其他来源。

### 五、分阶段数据流

企业研究阶段：

1. `validating-company`
2. `searching`
3. `fetching-pages`
4. `analyzing-company`
5. `matching-resume`
6. `generating-questions`
7. `completed | partial | failed`

企业来源按 URL 缓存；企业基础研究按企业与官网缓存；岗位研究按企业、岗位和 JD 单独保存。

高优先级问题必须同时拥有：

- 企业依据及 sourceIds；
- JD 依据；
- 简历 evidence/experience ID。

缺少三重依据的问题不得保持高优先级。

## 页面设计

### 岗位方向页

页首新增“获取岗位灵感”按钮与阶段式进度。页面主体展示持久化方向卡，而不是静态数组。

每张正式方向卡支持：

- 查看详细分析；
- 设为主方向或备选方向；
- 重新分析；
- 删除；
- 查看直接证据、迁移证据、缺口和搜索关键词。

岗位灵感使用现有设计语言的弹窗/抽屉，包含推荐卡、详情、保存、排除、换一批和类似方向操作。

### 面试准备页

保留现有五个 Tab，补充：

- 企业身份、官网、行业、来源数量、完成时间和置信度摘要；
- 真实分阶段进度；
- 每个来源的正文状态；
- 搜索、网页读取、企业分析、简历匹配、问题生成的独立重试入口；
- 高概率问题的企业、JD、简历三重依据。

## 错误与降级

岗位灵感区分档案不足、模型失败、解析失败和部分成功。

企业研究区分企业缺失、企业歧义、官网无效、搜索失败、搜索无结果、网页读取失败、千问鉴权、限流、超时、格式异常、Schema 异常和持久化失败。

任何后续阶段失败都保留先前成功来源与分析。没有可靠正文时不生成企业事实，但 JD 与简历分析仍可查看。

## 测试

测试按以下顺序增加：

1. 旧四方向迁移、无限新增、删除和状态变更。
2. 完整档案证据拆分与同证据多方向解释。
3. 岗位灵感 Schema、去重、反馈、换一批和部分成功。
4. 企业名称/官网端到端参数传递。
5. 官网优先、网页正文清洗、超时、重复内容和单页失败。
6. 企业分析引用 sourceId 且不在资料不足时编造。
7. 高优先级问题的三重证据约束。
8. 分阶段 UI、独立重试和旧记录补跑。
9. 全量测试、类型检查、生产构建和浏览器交互复核。

## 非目标

- 不引入新的第三方搜索 API Key。
- 不硬编码新的岗位名称模拟推荐。
- 不保存原始录音或完整模型上下文日志。
- 不重构与本需求无关的页面。
